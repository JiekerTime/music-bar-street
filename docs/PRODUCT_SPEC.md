# 一次演出合作怎么走

第一版先做酒吧与艺人之间的一次合作。注册和资料让双方能找到彼此，投递或邀请让双方开始聊，订单记录最后谈定的条件和演出结果。

## 入驻和资料

酒吧注册后填写场地资料、上传营业执照，审核通过再发布需求。艺人填写简介、作品视频、报价、档期和擅长风格。双方都能修改自己的主页。

视频和图片只是找人的参考，最终费用、可用档期和演出要求仍要确认。账号、资料和内容需要基本的审核与下架能力；一期放在业务服务里，配只读看板，暂不拆独立管理服务。

## 两个入口

**发需求**：酒吧写清楚日期、开始和结束时间、场地、预算、艺人类型及要求。艺人投递后，酒吧选人，再聊最后的条件。投递可以撤回或被拒绝，其他投递不能因为有人开始洽谈就被当成已成交。

**发邀约**：酒吧看过作品，向指定艺人发邀请。艺人可以拒绝，也可以表示愿意聊；接受邀请之后仍要确认条件。

一条需求可以收到多个投递。一期先支持一个需求确认一位艺人；多人需求以后再定义人数和费用规则。

## 商量条件

基本消息用于沟通，谈定后整理成一份双方都能看到的条件：

- 开始和结束日期、时间、时区；跨午夜演出必须有正确的结束日期。
- 场地、双方身份、演出形式和要求。
- 按场还是按小时，数量、单价、总费用和币种。
- 设备、彩排、交通等安排，以及取消和改期的约定。

酒吧预算和最终演出费分别保存，不能直接把预算当成交金额。条件每改一次就记一个版本，之前的确认作废，双方重新确认。

## 确认订单

只有双方确认了同一版条件，才生成已确认订单。此时保存条件快照，并再次检查艺人的档期。一位艺人不能被两个确认订单占用同一时段。

订单生成前，投递、邀约和洽谈各自保留状态。订单生成后，普通编辑不能直接改历史快照；改期或改价要提出变更，让双方确认，再保存新版本和旧记录。

重复点击确认只能产生一份订单。需求是否允许多位艺人、怎样算人数和金额，由实施者在需求规则中明确。

## 演出之后

演出结束，双方分别确认完成。一方先确认时，订单显示待另一方确认；双方都确认后才完成。如果有人不认可完成结果，进入争议处理，不能由一方直接覆盖结果。

取消或改期要记下发起方、原因和处理结果。订单前可以撤回本次洽谈；订单后按已经谈定的规则处理，不能直接删掉订单。是否有取消费用，由双方约定和运营规则决定。

演出费先由双方自行结算。订单完成、按 1% 统计的服务费、平台实际收款分开记录。会员购买和现金收款是另外的流程，第一版不把这两件事混在一起。

## 一期做到哪里

入驻、主页、需求、投递与邀约、基础消息、双方确认、演出记录和只读看板是第一版范围。会员先保留入口和权益设计，收费规则定下来后再实现。

直播、现金打赏、钱包、提现和粉丝数据放后面。页面目录保留这些职责说明，作为后续规划。

[低保真原型](../prototype/index.html) 描述一期的入驻、需求、投递、邀约、谈条件、双方确认、订单与完成页面。原型用灰色线框，公开资料不展示现有 UI。

## 页面设计需要讲清楚的事

报价始终显示单位、数量、单价和总价。需求发布、投递、改条件、双方确认和完成分别有清楚的状态与操作入口；条件更新、档期冲突、取消待回应和争议处理都不能只留成功状态。详见[页面职责](UI_MAP.md)和[原型说明](PROTOTYPE_DESIGN.md)。
